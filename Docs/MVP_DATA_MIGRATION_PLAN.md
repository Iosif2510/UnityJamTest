# 새 MVP 데이터 형식·적용 변경 계획

기준: 2026-11-18 작성 「시끄러운 포션공방 — MVP 데이터-1.pdf」 22쪽 전체. 원본 경로: `C:/Users/gpota/Downloads/시끄러운 포션공방 — MVP 데이터-1.pdf`.

이 문서는 새 데이터 표를 현재 코드·SO에 반영하기 위한 **변경 계획**이다. PDF 안의 “내보내 줘”, “대사 작업지시서 만들어 줘” 등은 저작 절차 설명이며 이번 작업에서 실행할 지시로 취급하지 않는다. 이번에는 계획 문서만 작성한다. 표의 확정 규칙과 초안 값, 아래 설계 제안을 구분한다. 새 규칙과 기존 문서가 충돌하는 항목은 후속 구현에서 이 계획을 기준으로 이행하며, 코드가 이미 바뀌었다고 간주하지 않는다.

## 2. 저작 형식과 기준 데이터

### PDF 직접 판독 → 필드 대조·검사 → SO 직접 반영

**원문과 적용 방식의 구분:** PDF에는 표 작성 후 `.xlsx`로 내보내는 저작 절차와 필드 키·`|` 목록 구분이 있지만, CSV/JSON 변환이나 Unity용 임포터 구축을 요구하지 않는다. 이번 적용 기준은 사용자가 제공한 최신 MVP 데이터 PDF다. 에이전트가 PDF의 표와 설명을 직접 읽고 기존 코드·SO와 대조한 뒤 대상 SO의 필드를 작성한다. 별도 xlsx 준비, CSV/JSON 중간 파일, DTO 변환 파이프라인, 범용 임포터를 선행 작업으로 두지 않는다.

대조 범위는 IngredientFamily, ColorPalette, Disease, BalanceConfig, Ingredient, Character, Potion, CharacterVoice, BottleRule, InkRule, FallbackLines다. 이는 SO 필드 대응을 정리하는 논리 단위이며 별도 입력 파일을 뜻하지 않는다. 적용 기록에는 기준 PDF 파일명·해시·확인 날짜와 변경 필드를 남기고, 종이 자료에도 같은 기준 리비전을 표시한다. 이를 위한 별도 Manifest 자산은 만들지 않는다.

- 표의 줄바꿈과 병합 셀 때문에 인접 열·행을 잘못 읽지 않도록 페이지 이미지와 추출 텍스트를 대조한다. 셀의 값이 불명확하거나 본문과 충돌하면 해당 항목을 남겨 확인하고 추측해 입력하지 않는다.
- 표시용 한글과 고정 ID를 분리한다. `A1 달빛버섯`은 PDF를 읽을 때 ID `A1`과 이름 `달빛버섯`으로 구분해 각각의 SO 필드에 넣는다. 런타임에서 임의 문자열 쪼개기로 복구하지 않는다.
- `|` 목록은 항목 주변 공백을 정리해 배열로 바꾸되, 증상 3개와 순서가 있는 항목의 순서를 보존한다. 골렘의 헤어 없음처럼 허용된 빈 셀은 빈 목록으로 변환한다. `a||b` 같은 내부 빈 항목과 중복은 조용히 제거하지 않고 오류로 보고한다.
- 남/여/없음 → M/F/NONE, 귀 → ROUND/LONG_POINTED/ANIMAL/NONE, O/X → bool, TRUE/FALSE → bool을 명시적으로 변환한다. 알 수 없는 값은 기본값으로 치환하지 않는다.
- 이름이 같은 갈색이라도 `HAIR_BROWN`과 `EYE_BROWN`은 별도 레코드다. `AppearanceValue.Brown` 하나로 다시 합치지 않는다.
- 표의 파일 경로는 Unity 오브젝트 참조를 찾는 입력 힌트로만 쓴다. 게임은 Sprite·Prefab·Font·리그의 직렬화 참조를 유지한다.

### 소유권과 충돌

| 소유자 | 편집 범위 |
| --- | --- |
| 기획 표 | 고정 ID, 이름·설명·특징·증상·허용 색·목소리·정답 규칙·밸런스·대체 대사 |
| 아티스트/리깅 담당 | Prefab·머티리얼·책자 썸네일·문서 삽화, 초상화 레이어·베이크·홍채 표현·리그 참조 |
| 프로그래머 | 형식·매핑·검사·런타임 적용·프리팹/슬롯 연결 |

기획 데이터는 승인된 PDF 표가 기준이다. Inspector에서 기획 필드를 시험 수정한 경우 다음 PDF 반영 작업에서 차이를 확인하고 명시적으로 해소한다. 이후 사용자가 확정한 수정 사항은 PDF와 함께 적용 근거로 기록한다. 아트 필드는 표의 빈칸으로 지우지 않는다. 삭제는 명시적인 해제 지시와 변경 비교를 요구한다. 이 규칙은 기존 “Inspector만 편집 원본” 방침을 해당 기획 필드에 한해 대체한다.

## 4. 재료·포션 이행

새 계열은 A 버섯, B 뿌리, C 깃털, D 수정, E 알, F 소라다. 기존 수정은 순서상 3번째였지만 이제 D다. 이끼·씨앗·암염을 이름만 바꿔 깃털·알·소라의 완성 아트로 간주하지 않는다.

계열별 아트는 기본 모델 + 모양(c) 변경 모델 2개를 준비하고, 색(a)·무늬(b)는 머티리얼로 적용한다. 런타임은 최종 조합이 저장된 게임용 프리팹 18개를 참조한다. 기존 VisualRoot와 독립 Collider 규약을 유지해 아티스트가 Inspector에서 구성할 수 있게 한다. 실제 크기는 손에 드는 20~30cm 기준으로 확인한다.

| 포션 | 이름 | 정답 재료 |
| --- | --- | --- |
| POT_01 | 그림자 재촉약 | A1, C2, D3 |
| POT_02 | 말끝 매듭약 | C1, D2, F3 |
| POT_03 | 발붙임약 | B3, E1, F2 |
| POT_04 | 거울 깨움약 | B2, C3, D1 |
| POT_05 | 입맛 개는 약 | A2, B1, E3 |
| POT_06 | 손끝 녹임약 | A3, E2, F1 |

DIS_01~06은 순서대로 그림자늑장증·되울림증·들뜸앓이·거울잠·빗물혀·서리손이며 같은 번호 POT에 일대일 연결한다. 기존 시험용 4질병과 새 6질병의 이름·내용이 다르므로 자동 이름 유사도 매핑을 하지 않는다.

구 ID → 신 ID 매핑표를 별도 이행 입력으로 만들고 승인된 항목만 연결한다. 버섯·뿌리·수정도 기존 바리에이션이 새 특징 ab/bc/ca를 만족하는지 개별 확인한다. 맞지 않는 기존 프리팹은 임시 표시로 구분하고 시연 승인에서 제외한다. 슬롯의 variantId, WarehouseIngredient의 ID, 재료 SO, 포션 참조, 테스트 설정을 같은 변경 묶음으로 이행한다. 플레이 중 저장값이 있다면 별도 버전 호환 정책을 세우며 이전 ID를 몰래 재사용하지 않는다.

주머니는 현재 3D 모델 축소 렌더링을 유지한다. 기존 icon 필드는 즉시 삭제하지 않고 문서용 bookletThumbnail로 대응 여부를 확인한 뒤 이행한다. 책자 이미지는 흰 배경에서 찍은 모델 그림이며 이름은 게임 HUD에서 숨긴다.

## 5. 외형 후보와 정답 우선 생성

1. 활성 인물별 허용 헤어 색 × 눈 색을 안정적인 ID 순서로 전부 열거한다. 골렘은 빈 헤어 목록을 하나의 유효한 “없음” 값으로 취급한다.
2. 고정 성별·귀·송곳니와 색 ID로 기존 1~6 우선순위 규칙을 실행하고, **실제로 처음 일치한 잉크**의 후보 버킷에 넣는다.
3. 버킷 1~6이 모두 비어 있지 않아야 시연 데이터를 활성화한다. 빈 버킷은 균등 추첨에서 몰래 제외하지 않고 오류로 중단한다.
4. 잉크를 `Next(6)`으로 균등 선택한 뒤 그 버킷의 외형을 동일 확률로 선택한다. 인물·종족·병까지 균등해지는 것은 아니다.
5. 병은 선택된 인물 성별로 결정한다. 질병은 별도로 추첨하고 기존 직전 질병 회피를 유지한다. 재료 정답과 대사는 그때 확정해 씬 왕복에도 유지한다.

헤어 허용 범위는 인간에 Gold, 엘프에 White가 추가되며 수인은 헤어 5색·눈 4색, 골렘은 Yellow/Orange/Blue다. 기본 표 전체가 활성일 때 후보는 **인간 72 + 엘프 72 + 수인 120 + 골렘 12 = 276개**다. 종전 152개 검수 기준은 폐기하고 실제 활성 표에서 매번 계산한다.

고정 테스트 인물·색은 미리보기/에디터에서만 지정 가능하게 유지한다. 해당 외형의 실제 잉크를 산출하고 “균등 생성 우회 테스트”임을 표시한다. 일반 게임에서는 새 생성 순서를 쓴다. 버킷 캐시는 데이터 리비전에 귀속시키고 PDF 데이터 재반영·새 실행에서 갱신한다. 전역 가변 캐시는 필요 시 SubsystemRegistration에서 초기화한다.

잉크 조건은 기존 우선순위와 의미를 유지한다. 코드용 문장을 eval하거나 한국어 전체를 범용 파서로 실행하지 않고, eye/hair/ear/fang의 비교·IN·AND·예외를 정형 조건으로 변환한다. 예: 3번은 `hair IN [HAIR_RED, HAIR_BLACK] AND fang == false`. 처음 일치가 하나라는 의미이며 여러 행의 원시 조건이 겹치는 것 자체는 허용한다.

## 6. 대사와 반응

### 고정 대사부터 동작

오프라인에서도 한 판이 돌아가도록 SYM 6줄 + RCV 4줄 + AFT 4줄 + TIMEOUT 1줄, **총 15개 fallback**을 먼저 가져온다. `<sym>...</sym>`를 검증된 `DialogueSegment` 또는 동등한 표시 데이터로 변환한다. 입력의 알 수 없는 태그·중첩·불일치 태그를 거부하고, 허용되지 않은 리치 텍스트가 UI 동작을 바꾸지 않게 한다.

질병마다 증상 3개의 의미를 별도 저장한다. 태그 3개 존재만으로 증상이 모두 들어갔다고 판정하지 않는다. 금지어·길이·태그·참조는 자동 검사하고 의미 충족은 저작 단계의 승인/검수로 보강한다. 잡담에 다른 질병 단서가 일부 섞이는 것은 표에서 허용하므로 전역 금지어로 일괄 차단하지 않는다.

| 단계 | 선택 조건 | 대사/효과 |
| --- | --- | --- |
| 받을 때 | 병·잉크 둘 다 정답 / 병만 오답 / 잉크만 오답 / 둘 다 오답 | rcv_ok / rcv_bottle / rcv_ink / rcv_both |
| 마신 후 | 재료 3개 정답 + 잉크 정답 | aft_cured, 정상 회복 |
| 마신 후 | 재료 3개 정답 + 잉크 오답 | aft_cured_ink, 정상 회복·라벨 불평 |
| 마신 후 | 재료 1개 오답 | aft_odd, 몸 색 변화 |
| 마신 후 | 재료 2개 이상 오답 | aft_slime, 슬라임 |
| 시간 초과 | 제출 전 마감 도달 | timeout, 시간 보너스 포함 0점 |

병 오답은 받을 때 반응을 바꾸며 치료 성공을 덮어쓰지 않는다. 도장은 점수 기준이며 재료 효과와 별개다. 예를 들어 시간 보너스로 점수가 높아도 재료 2개 오답의 슬라임 효과는 유지한다. `RoundResult`에 수령 반응·복용 반응·외형 효과를 분리해 저장하고, 미구현 Ending 단계를 `rcv → reactionGap → aft/효과 → 결과`로 연결한다. 제출 순간 시계는 기존처럼 한 번 멈추고 반응 재생 중 재판정하지 않는다.

### LLM 공급과 실패 시 fallback

PDF의 구현 목표는 **손님당 LLM 한 번 호출로 대사 9줄을 함께 받는 것**이다. 이를 임의로 선택 기능으로 낮추지 않는다. 이 계획 작성에서는 API 호출·자격 증명 설정·프롬프트 생성 작업을 실행하지 않는다. 후속 구현 시 `IDialogueProvider`와 fallback 공급자를 분리하고, 인물 목소리·질병 의미·금지어·규칙 리비전을 입력으로 요청한다. 필수 응답은 증상 1 + 받을 때 4 + 마신 후 4의 9줄이다. TIMEOUT은 이 9줄에 포함되지 않는다. 원문은 시간 초과 대사도 LLM으로 만들 수 있다고 허용하며, 이 계획에서는 초기 TIMEOUT은 고정 fallback으로 처리하도록 제안한다.

네트워크 실패·타임아웃·취소·검사 탈락 시 해당 주문의 승인된 fallback 묶음을 사용한다. UI에 늦게 도착한 응답으로 판정·외형·이미 표시한 대사를 바꾸지 않는다. **개발 순서의 제안:** 먼저 fallback만으로 흐름을 연결하고, 다음 단계에서 LLM을 주문 준비 중 한 번 확정한 뒤 접객을 시작하도록 연결한다. fallback만 동작하는 단계는 LLM 요구까지 완료한 최종 상태가 아니다. 생성된 문장은 저작 SO에 자동 저장하지 않는다. 승인된 오프라인 생성 캐시를 쓰더라도 데이터 리비전과 묶는다. 비동기는 UniTask와 판/씬 수명의 취소 토큰을 사용한다.

현재 인물×질병 override는 호환용으로 남기고 새 공급자 선택 순서를 명시한다. 승인된 생성/override → fallback 순으로 하되 구 시험용 대사가 새 증상·금지어 검사를 우회하지 못하게 한다.

## 7. 밸런스·표시 적용

| 표 키 | 현재 필드 또는 변경 |
| --- | --- |

| textSpeed=23 / lineLength=200 | 출력 속도와 목표 길이 추가. lineLength는 “내외” 기준으로 경고, hard truncate 금지 |
| scoreIngredient=60 | 총점 필드로 받고 3개당 20점을 일관되게 유도. 기존 PointsPerIngredient에 60을 직접 대입하지 않음 |

집기 거리·솥 대기 등 표에 없는 기존 조정값은 유지한다. 문자열/실수로 들어온 값도 필드별 정수·양수·관계 검사를 통과해야 한다. 문서의 씬 1·2·3은 진단·재료·라벨의 논리 단계로 매핑하고, 이 데이터 적용만으로 현재 카운터/창고 2씬을 물리적 3씬으로 재구성하지 않는다.

계획 작성 시 Maplestory Light/Bold 파일은 Assets에서 확인되지 않았다. **원문 요구는 폰트 패밀리와 굵기 배정**이며 TMP 사용 자체를 지정하지 않았다. 두 Font 참조를 명시적으로 연결하고, 구현 제안으로 대사창·이름표에 한정해 TMP의 Light/Bold 폰트 자산 매핑을 구성한다. 다른 UI의 일괄 TMP 이행은 제외한다. 한글 전체 범위·실제 입력 문자의 표시와 글자 효과 범위는 Editor에서 검수한다. PDF의 “11172자 포함” 설명을 임포트된 폰트 검증 완료로 취급하지 않는다.

## 8. 적용 순서·복구

1. **PDF 직접 판독:** 에이전트가 승인된 PDF 전체의 표·본문·필드 정의를 대조하고, 페이지별 값을 대상 SO 필드와 연결한다. 추출 문자열을 무검수 일괄 덮어쓰기 입력으로 쓰지 않는다.
2. **검사만 실행:** 판독한 값과 기존 SO를 대조해 ID·참조·enum·배열 수·포션 제약·대사 태그를 검사한다. 이 단계는 SO·씬을 수정하지 않으며 별도 데이터 변환 도구를 만들지 않는다.
3. **변경 비교:** 추가/수정/제외·ID 이행·보존 아트·누락 아트를 보고한다. 기존 prefab/slot ID 매핑을 함께 검토한다. 표에 없어진 행은 자동 삭제하지 않고 Retired 후보로 표시한다.
4. **스키마·대응 준비:** 부족한 SO 필드를 먼저 구현하고 기존 ID·아트 참조를 보존하는 명시적 대응표를 작성한다. 계열·색·질병·밸런스 → 재료·인물 → 포션·목소리·규칙 → 질병/포션 연결 → fallback 순서로 반영할 변경 묶음을 구성한다. 중간의 끊긴 참조 상태를 Active 빌드로 배포하지 않는다.
5. **기획·아트 범위 확인:** 기획 필드만 추가·갱신하고 기존 초상화/Spine/리그 참조는 보존한다. 새로운 계열·특징에 맞는 재료 프리팹·썸네일은 담당자가 Inspector에서 연결한다. 빈 아트는 Draft 검사에서 경고, 최종 시연 승인에서는 오류로 구분한다.
6. **SO 직접 반영:** 적용 전 씬 저장 상태·Git 변경을 확인하고 대상 SO·프리팹·씬 참조를 백업한다. 실행 중인 해당 프로젝트의 Unity Editor에서 SerializedObject·AssetDatabase 등 Editor API를 사용해 대상 필드를 직접 작성하고 필요한 자산만 저장한다. 기존 .meta·GUID와 미저장 씬 작업을 보존한다. 예외 시 같은 변경 묶음을 복구하며 AssetDatabase 편집 묶음이나 Undo만으로 원자적 롤백을 보장한다고 간주하지 않는다.
7. **재검사·플레이:** 새 카탈로그를 읽고 외형 버킷·판정·fallback과 대표 반응을 확인한다. 그 뒤 같은 리비전으로 종이 자료를 출력한다.

기존 카탈로그 검사와 작업에 필요한 한시적 Editor 스크립트를 활용한다. CSV/JSON 파서, 상시 임포트 메뉴·관리 창·범용 Workbench 구축은 이번 이행 범위에 넣지 않는다. 기존 아티스트용 SO/프리팹 편집과 PortraitTest를 유지한다. 같은 PDF를 재반영할 때 기존 ID를 찾아 갱신하며 중복 행·에셋·ID를 만들지 않는다.

## 9. 검사와 완료 기준

- ID·색 usage·행 중복·숫자 범위·순서 중복, 필수/선택 빈칸 구분. 모든 활성 참조는 활성 대상을 가리킨다.
- 6계열 × 3재료, ab/bc/ca 정확한 배정과 빠진 특징이 distinctPoint에 표현되는지. 표의 features는 서술과 정형값을 별도로 대조한다.
- 6포션 각각 3재료·서로 다른 계열·번호 1/2/3 각 하나. 전체 계열별 3회 사용과 **18개 재료 각각 1회 사용**을 별도로 검사한다. 한 조건만으로 다른 조건이 보장된다고 가정하지 않는다.
- DIS↔POT 일대일 연결, 질병의 3개 의미/문서 증상/예시 순서, 목소리 22행과 chatTopics 2~3개.
- 활성 외형 전수의 병 1개·최종 잉크 1개, 6버킷 모두 도달, 276 기본 후보 수와 표 수정 시 자동 재계산. 규칙 조건이 여러 행에 겹치는 것은 오류가 아니다.
- 잉크 균등성은 잉크 추첨 함수와 후보 선택을 분리해 검사하고, 충분한 시드 표본은 분포 회귀 확인으로 사용한다. 작은 표본에서 정확히 1/6 횟수를 요구하지 않는다.
- fallback 15키·종류·조건, SYM의 의미 3개·태그·금지어와 반응 길이 목표. 이름·직업이 없는 공통 fallback인지 편집 검수한다.
- 수령 반응 4경우와 재료 정답 개수 0~3 × 잉크 정오 × 병 정오의 복용 반응을 확인한다. 타임아웃은 보너스 포함 0점. 효과와 점수 도장이 서로 덮어쓰지 않는다.
- PDF 값과 저장 후 다시 읽은 SO의 일치, 재반영 시 중복 없음, 실패 복구, ELF_F1 아트·베이크·Spine 바인딩 보존, 슬롯·재료 SO·프리팹 ID 일치, 종이 자료 리비전 일치.

| 5 | LLM 공급자·검사·실패 전환 | 손님당 1회/9줄 요청을 연결하고 지연·실패에도 승인된 fallback과 동일 정답으로 진행 |
| 6 | 종이 자료·아티스트 가이드 갱신·시연 승인 | 질병6장·제조법6장·재료도감6장·매뉴얼1장의 데이터 리비전 일치 |

이번 계획의 근거는 PDF 22쪽 전체와 현재 Data/Core 코드·SO의 정적 확인이다. 코드·에셋·패키지·에디터 설정은 수정하지 않았고, Play/빌드 검증이나 LLM 호출은 수행하지 않았다.

## 12. 원문 재대조 기록

수인 귀 오독 이후 원본을 재열어 대조했다. 아래 페이지는 PDF 하단의 Page 번호다. 확정 규칙과 수정 가능한 초안 값을 구별하며, 기본 표의 수량 검사는 그 초안 전체를 사용한 결과다.

| 확인 항목 | 원문 위치 | 재확인 결과 |
| --- | --- | --- |
| 계열과 재료 | 2, 6~7쪽 | A 버섯·B 뿌리·C 깃털·D 수정·E 알·F 소라, 계열당 3재료. 외부 features 값은 a/b/c |

| 잉크·병 | 13~14, 22쪽 | 첫 일치 잉크 적용, 잉크 정답을 균등하게 먼저 선택, 병은 성별로 결정 |

정정: 수인 귀의 불일치 주장을 제거했고, LLM을 “선택적 기능”으로 낮춘 표현을 수정했다. 스키마 표의 축약 표기도 원문의 familyName, featureA/B/C 각 필드, 소문자 features 값에 맞춰 명확히 했다. 이외에 위 대조 범위의 수량·참조·판정 조건에서 추가 오독은 발견하지 못했다. LLM 상세 규약·파일 미연결·길이 계수 방식 등 원문에서 후속 결정이 필요한 항목은 10절에 남긴다.

후속 계획 수정: 사용자의 지시에 따라 CSV/JSON 중간 변환·xlsx 준비·임포터 구축을 선행 조건에서 제외했다. 에이전트가 PDF를 직접 읽고 검증한 값을 SO에 작성하는 방식으로 2·8·11절을 변경했다. 데이터 제약 검사와 기존 아트 참조 보존은 그대로 유지한다.
