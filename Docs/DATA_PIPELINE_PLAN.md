# 인게임 데이터 직렬화와 제작 파이프라인

새 MVP 표의 후속 이행은 [MVP 데이터 형식·적용 변경 계획](MVP_DATA_MIGRATION_PLAN.md)을 참고한다. 에이전트가 최신 PDF를 직접 읽고 기존 필드와 대조·검사한 뒤 SO에 반영한다. CSV/JSON 변환·xlsx 준비·임포터 구축은 선행 조건으로 두지 않는다. 새 ID와 재료 계열, 정답 잉크 우선 생성, 목소리·fallback·반응 분리를 계획했다. 아래 문서의 Inspector 원본 편집·외형 우선 생성 설명은 기존 구조이며, 새 계획의 구현 완료를 뜻하지 않는다. 아트의 직접 연결과 기존 바인딩 보존 원칙은 유지한다.

손님·질병·레시피·재료·처방 규칙을 **Unity Inspector에서 편집하고, 편집 자료를 판 시작 전에 읽기 전용으로 구성**한다. 기획과 아트가 같은 목록을 편집하지 않도록 소유권 단위로 파일을 나눈다. 개발 중에는 Inspector 편집, 데이터 검사, 주문 미리보기까지 우선 구축한다.

손님 초상화는 업데이트된 작업지시서를 우선한 [손님 초상화 구성 시스템 확정 계획](CUSTOMER_PORTRAIT_PLAN.md)을 따른다. 부위별 Sprite 추첨은 고정 인물 + 허용 색 조합으로 교체한다. 이 문서는 목표 파이프라인이며 현재 구현 완료 상태와 구별한다.

아티스트의 재료 모델·초상화·UI 적용과 화면 검수는 [아티스트 에셋 적용·플레이 테스트 계획](ARTIST_WORKFLOW_PLAN.md)을 따른다. SO·프리팹 Inspector에서 직접 연결·저장하고 고정 조건으로 실제 플레이하며 확인한다. 경로·파일명은 정리 규칙으로 쓰고 게임 연결은 직렬화 참조를 사용한다. 카탈로그 참조 변경이 실제 씬 진열·코드 생성 UI에 반영되는 연결과 빠른 테스트 진입을 우선하며, Art Workbench·독립 시각 프리뷰·폴더 자동 연결은 후순위다.

초상화에 한해 PortraitTest 개발용 씬에서 실제 표시 모듈별 연결·재생을 먼저 확인한다. 선택한 Draft 인물도 전체 질병·레시피 데이터 없이 검사할 수 있게 하고, 씬 로컬 덮어쓰기와 원본 SO 저장을 구분한다. 최종적으로 덮어쓰기를 끈 SO 입력으로 재현하고 실제 카운터 통합 검수를 거친다. 재료·일반 UI용 별도 씬은 추가하지 않는다.

## 저장 구조

```text
Assets/GameData/
├─ PotionCatalog.asset           # 카운터 RoundRoot의 단일 콘텐츠 참조
├─ Customers.asset               # 고정 인물 22명, 레이어·고정 속성·허용 색·눈 영역·리그, 슬라임
├─ PortraitColors.asset          # 헤어·눈 공용 색 ID, 이름, 단일 색 값
├─ DiseasesAndRecipes.asset      # 질병, 대사, 레시피
├─ Ingredients.asset             # 재료 종류와 종류별 바리에이션, 프리팹, 아이콘
├─ PrescriptionRules.asset       # 성별별 병, 순서가 있는 잉크 규칙
└─ RoundTuning.asset             # 제한 시간, 주머니 칸, 집기 거리, 점수
```

- `PotionCatalog`에는 하위 에셋 참조만 둔다. 각 하위 에셋은 `[Serializable]` 레코드의 리스트를 가진 ScriptableObject다. 구현 시 에셋과 `.meta`를 함께 버전 관리한다.
- **콘텐츠 간 관계는 고정 ID**로 연결한다. 예를 들어 `disease.shadow_lag → recipe.shadow_sync → ingredient.mooncap.blue`다. 화면 이름, 배열 위치, 번역된 문자열은 바뀌어도 관계가 유지된다. 일반 콘텐츠 ID는 영역 접두사를 포함한 영문 소문자·숫자·밑줄·점으로 제한한다. **인물 ID는 새 작업지시서 호출코드(HUM_M1, GOL_G1 등)를 그대로 쓰는 예외**이며, 로더에서 별도 형식을 검사하도록 이행한다. 활성 여부와 관계없이 각 영역 안에서 유일해야 한다. 색은 `color.brown`처럼 고정 ID로 참조한다.
- **표시용 에셋은 Unity 오브젝트 참조**로 연결한다. 초상화는 Sprite, 재료는 프리팹과 Sprite를 지정한다. 같은 모델을 새 경로로 이동할 때는 Unity에서 이동하거나 기존 `.meta`를 함께 옮긴다.
- 직렬화 필드 이름을 바꿀 때는 `FormerlySerializedAs`로 기존 값을 읽고, ID 변경은 별도의 참조 수정으로 다룬다. 외형 속성은 형식이 정해진 값으로 둔다. 예를 들어 `귀 없음`은 누락된 값과 구분되는 유효한 선택이다.

| 영역 | 최소 필드와 관계 | 편집 시 주의점 |
| --- | --- | --- |
| 손님 생성 | 고정 인물 호출코드, 종족·variation·성별·직업·귀·송곳니, BASE/EYE_CLOSED/헤어 레이어, 허용 색 ID, 홍채 영역, 리그. | 입·귀·헤어 모양은 고정이다. 골렘 헤어와 짧은 머리의 뒷머리 없음은 유효하다. 눈 색·귀·송곳니는 파일명에서 읽지 않는다. |
| 초상화 색 | 색 ID, 표시 이름, Color 1개. | 헤어는 밝은 회색조에 곱하고 홍채는 엔진 생성 면에 적용한다. RGB를 바꿔도 판정 ID는 유지한다. |
| 질병·대사 | ID, 표시 이름, 잡담과 증상 구간을 구분한 공통 대사 후보, 레시피 ID. 선택적으로 인물 ID × 질병 ID 전용 대사. | 정확히 일치하는 전용 대사를 우선하고 없으면 질병 공통 대사를 쓴다. 종이 카드와 같은 증상을 가리켜야 한다. |
| 레시피 | ID, 종이 제조법에 표시할 포션명, 서로 다른 3종에서 하나씩 고른 바리에이션 ID 3개. | 정답은 실제 바리에이션 ID로 비교한다. 같은 종류의 다른 바리에이션도 오답이다. |
| 재료 | 종류 ID 및 바리에이션 3개. 각 바리에이션은 고정 ID, 표시 이름, 프리팹, 주머니·인쇄 자료용 이미지를 가진다. | 창고에는 서로 다른 종류 6종을 진열하고, 선반 하나에는 해당 종류의 바리에이션 3개를 함께 놓는다. 재료 이름은 게임 HUD에서 숨긴다. |
| 처방 | 성별 → 병 매핑, 잉크 규칙마다 ID·조건·예외·결과 번호. | 잉크는 목록의 위에서부터 처음 맞는 한 줄을 적용한다. 마지막에 조건 없는 기본값 한 줄을 둔다. |
| 밸런스 | 전체 제한 시간, 집기 거리, 솥 대기 시간, 점수와 도장 구간. 주머니는 레시피 재료 수와 같은 3칸으로 고정한다. | Inspector 범위 지정으로 입력 실수를 줄이고, 최종 유효성은 데이터 검사에서 확인한다. |

## 편집에서 게임까지

`Inspector 편집 → 데이터 검사 → 시드 주문 미리보기 → 승인된 데이터와 종이 자료 함께 반영 → 빌드`

### 추가·수정·제외

1. **추가**는 하위 에셋에서 새 ID를 발급하고 `Draft` 상태로 시작한다. 예를 들어 재료 종류를 추가할 때는 바리에이션 3개에 각각 ID·모델·아이콘을 연결한다. 레시피와 참조가 준비되면 `Active`로 바꾸고 검사를 실행한다.
2. **수정**은 이름, 그림, 대사, 조정값을 해당 항목에서 바꾼다. ID나 잉크 규칙 순서처럼 결과를 바꾸는 수정은 사용처와 주문 미리보기를 함께 확인하고, 종이 자료에 같은 변경을 반영한다. 활성 데이터끼리 연결된 여러 에셋을 바꾸면 같은 변경 묶음으로 반영한다.
3. **제외**는 `Retired`로 전환한다. 예를 들어 재료 종류를 빼려면 그 종류의 바리에이션을 쓰는 활성 레시피의 참조를 교체하거나 함께 비활성화한다. 활성 종류에는 바리에이션이 항상 3개 있어야 하므로 바리에이션 교체와 레시피 수정은 한 번에 반영한다. 사용처 조회에는 질병 → 레시피, 레시피 → 바리에이션, 종류 → 바리에이션 관계를 표시한다. 남은 참조가 있다면 삭제 작업을 중단한다. 제외된 ID는 재사용하지 않는다.
4. **원복**은 해당 Unity 에셋과 종이 자료에 대한 변경을 함께 되돌린다. 게임에서 생성한 주문과 제출값은 `RoundState`에만 저장되므로 플레이 자체로 저작 에셋이 바뀌지 않는다.

### 런타임 로드와 주문 생성

- 카운터 진입 시 `CatalogLoader`가 에셋을 한 번 읽어 활성 항목과 ID 조회표를 만든다. 작성용 리스트는 직렬화에 쓰고, 딕셔너리는 런타임 로드 후에 만든다. 입력 에셋을 다시 읽거나 수정하는 작업은 씬 전환마다 하지 않는다.
- 로드가 성공하면 `OrderGenerator`가 종족 → 고정 인물 → 허용 헤어/눈 색을 선택하고, 고정 성별·귀·송곳니를 결합한다. 질병은 독립적으로 고르고, 활성 질병이 둘 이상이면 직전 질병을 피한다. 인물·질병 전용 대사 또는 질병 공통 대사를 선택한다. 외형에서 병·잉크 정답을 계산하며 잉크 정답을 먼저 뽑지 않는다. 레시피의 재료 ID와 정답을 그 시점에 확정해 카운터와 창고가 같은 주문을 사용하게 한다.
- `PotionCatalog`에는 신규 색 카탈로그 참조를 추가한다. 기존 CustomerProfile/PortraitPart와 인물 ID를 새 스키마·호출코드로 이행하고, 검증·사용처·주문 미리보기도 함께 갱신한다. `.meta`와 다른 콘텐츠 ID는 보존한다. 초상화 파일을 다시 읽어 매번 런타임 조립 데이터를 생성하지 않는다.
- 활성 데이터의 필수 참조나 값이 잘못되면 대기 화면에서 주문 시작을 막고, 콘솔에 에셋과 항목 ID를 남긴다. 임의의 레시피로 교체하거나 활성 항목을 조용히 건너뛰면 종이 자료와 다른 게임이 만들어질 수 있다.
- 저작 데이터에 대한 출력은 단방향으로 둔다. 종이 자료 작업에 포션명, 재료·이미지, 병·잉크 규칙 순서를 담은 대조표를 전달한다. 인쇄물과 시연 빌드를 확정할 때 같은 데이터 리비전을 표기한다. 게임잼 안에서는 대조표 내보내기를 선택 작업으로 두고, 규칙 편집은 Unity에서 진행한다.

## 에디터에서 확인하는 방법

Inspector로 편집하고, Unity 메뉴 `Potion Shop/Data` 아래에 작은 도구 세 개를 둔다. 에디터 코드와 메뉴는 빌드에 포함하지 않는다.

| 도구 | 확인 내용 |
| --- | --- |
| **Find Usages** | ID 하나를 입력하면 참조하는 활성·초안·제외 항목의 에셋과 ID를 보여준다. 제외·삭제나 ID 변경 전에 사용한다. |
| **Validate Catalog** | 중복·빈 ID, 활성 항목의 누락 참조, 인물 호출코드·고정 속성·필수 레이어·허용 색·홍채 영역·리그, 전용 대사 참조, 레시피의 서로 다른 재료 종류 3개, 활성 종류당 바리에이션 3개, 창고 선반 6곳의 진열 공급, 필요한 프리팹·이미지, 병 매핑, 잉크 기본값, 시간·점수 범위를 확인한다. 항목을 선택하면 해당 에셋으로 이동한다. |
| **Preview Order** | 시드와 직전 질병 ID를 받고, 필요하면 질병·외형을 고정해 실제 `OrderGenerator`로 한 주문을 만든다. 대사, 외형 속성, 정답 재료·병·잉크, 적용된 잉크 규칙 ID를 에디터에만 표시한다. |

- **오류와 경고를 구분한다.** 중복 ID, 끊긴 활성 참조, 잉크 기본값 누락 등은 반영을 막는 오류다. 편집 중인 초안의 누락 에셋, 생성 가능한 외형에 한 번도 적용되지 않는 잉크 규칙은 경고로 보여준다. 규칙이 겹치는 경우는 허용하고 우선순위로 어떤 규칙이 적용되는지 보여준다.
- **잉크는 시드 표본만 보고 끝내지 않는다.** 활성 인물 × 허용 헤어 색 × 허용 눈 색(골렘은 헤어 없음)의 전체 조합을 나열해 각 조합에 병과 잉크 결과가 있는지, 각 규칙이 몇 조합에 적용되는지 보고한다. 귀·송곳니는 인물 고정값이다. 초기 22명 목록은 152조합이며, 규칙 표를 수정하면 해설서 순서도 함께 갱신한다.
- **미리보기는 재현에 쓴다.** 같은 데이터 리비전, 시드, 직전 질병 ID에서 같은 주문이 나오도록 전용 난수 객체와 고정된 후보 순서를 사용한다. 개발 중 생성 입력 세 값을 함께 남기면 에디터에서 같은 주문을 다시 뽑을 수 있다. 고정 질병·외형 입력은 미리보기에서만 쓰며 원본을 변경하지 않는다.
- **데이터 확인과 플레이 검증은 별개다.** 조합과 참조는 메뉴로 확인할 수 있다. 시연 전 플레이 검증이 필요하다면, 데이터 때문에 화면과 종이 자료가 어긋날 가능성이 있는 경로를 먼저 특정하고 진행 여부를 묻는다. 매 편집마다 Play Mode를 열거나 테스트를 자동 실행하지 않는다.

대표 확인 시나리오는 **서로 다른 3종을 쓰는 레시피가 생성되는 경우**, **정답 대신 같은 종류의 다른 바리에이션을 제출하는 경우**, **잉크 예외를 건너뛰어 다음 규칙이 적용되는 경우**, **활성 레시피가 쓰는 재료를 제외하려는 경우**다. 앞의 두 경우 중 실제 창고 집기·제출 동작은 Play Mode 확인 범위이며, 주문에 정답이 어떻게 들어가는지는 미리보기에서 확인한다.

## 도입 순서

| 순서 | 구현 범위 | 끝내는 기준 |
| --- | --- | --- |
| 1 | 에셋 스키마와 ID 규칙, 활성 데이터 로드 | 임시 손님과 질병 2종, 3종 × 3개 바리에이션, 3종 레시피 2개를 Inspector에서 만들고 참조를 읽을 수 있다. |
| 2 | 주문 생성기를 연결하고 데이터 검사 메뉴 추가 | 저장한 데이터가 다음 미리보기와 새 실행에 반영되고, 잘못된 활성 참조는 에셋과 ID를 포함한 오류로 확인할 수 있다. |
| 3 | 시드 미리보기와 사용처 조회 연결 | 플레이를 시작하지 않고 주문을 재현하고, 항목을 제외하기 전에 영향 범위를 볼 수 있다. |
| 4 | 종이 자료 대조와 시연용 리비전 확정 | Unity의 포션·재료·잉크 값과 시연 종이 자료가 같은 출처에서 작성된 상태로 묶인다. |

일정이 밀리면 통합 작업창·독립 시각 프리뷰·폴더 자동 연결·자료 이미지 출력부터 미룬다. SO·프리팹 직접 연결이 실제 게임에 반영되는 경로, 고정 조건 플레이 진입, 누락 참조 검사와 대상 에셋 바로가기를 우선한다. 시드 주문 미리보기는 데이터 재현 도구로 유지하되 별도의 렌더링 창을 필수로 두지 않는다.
